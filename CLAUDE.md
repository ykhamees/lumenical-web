## What this is

The marketing site for Lumenical (lumenical.com) — a Next.js 16 App Router site, statically exported and deployed to Firebase Hosting. Six pages, no server, no database, no test suite.

## Commands

```bash
npm run dev              # dev server, localhost:3000
npm run build            # static export to out/ — this IS the deploy artifact
npm run lint             # eslint .
npx tsc --noEmit         # type-check (no separate script in package.json)
```

There is no test suite and no `test` script — don't invent one unassisted. Before reporting any non-trivial change as done, run `npm run build`, `npm run lint`, and `npx tsc --noEmit`; the `pre-deploy-check` skill (`lumenical-qa` agent) automates this plus route spot-checks and drift checks.

`out/` is regenerated by `npm run build` and `.next/` by `dev`/`build` — both are hook-blocked from direct edits (`.claude/hooks/guard-generated-files.js`). Fix the source instead. A `PostToolUse` hook also auto-lints every `.ts`/`.tsx` file after Write/Edit.

## Architecture

**Routing**: one folder per route under `src/app/` (`/`, `/services/`, `/about/`, `/contact/`), each a `page.tsx`. `next.config.mjs` sets `output: "export"` and `trailingSlash: true` — this must survive any Next.js upgrade, since the site ships as static HTML with no server runtime. Adding a route means creating the folder, registering it in `navLinks`/`footerLinks` (`src/content/site.ts`) if it belongs in nav, and adding it to `src/app/sitemap.ts`'s `routes` array.

**Content lives in `src/content/`, not inline in JSX**: `site.ts` (name, tagline, nav links, homepage stats/differentiators) and `services.ts` (the `services` array). Both `src/app/page.tsx` (homepage teaser cards) and `src/app/services/page.tsx` (full numbered list, anchored by `slug`) map over the same `services` array directly — adding/removing/reordering an entry there is the entire change, no separate registration. Lumenical is explicitly scoped to exactly six service disciplines; a request for a 7th that doesn't clearly fit one of the existing six needs a check-in rather than being added on assumption.

**Per-page SEO** goes through `pageMetadata()` in `src/lib/seo.ts`, not a bare `export const metadata`. Next.js does not deep-merge a page's `Metadata` with the root layout's — a page that sets only `title`/`description` silently inherits the layout's `openGraph`/`twitter` objects unchanged (wrong title/url in social previews). `pageMetadata({ title, description, path })` fills in the matching `openGraph`/`twitter`/canonical fields; use it in every page.

**Design tokens**: colors (`ink`, `paper`, `signal`, `lumen`, `success`) and font families are defined once in `tailwind.config.ts` and consumed as Tailwind classes — never introduce a raw hex color in a component. Fonts are `next/font/google` (Geist / Instrument Serif / JetBrains Mono) loaded once in `src/app/layout.tsx` and exposed as CSS variables (`--font-sans` etc.); don't add a second font-loading path. Brand voice is restrained, sentence case, no exclamation points, serif italic reserved for one statement per section — the `write-copy` skill / `lumenical-content` agent encode this.

**Forms degrade gracefully with no backend wired**: `NewsletterForm.tsx` and `ContactForm.tsx` both simulate success locally unless `NEXT_PUBLIC_NEWSLETTER_SCRIPT_URL` / `NEXT_PUBLIC_CONTACT_FORM_ENDPOINT` are set (see `.env.example`). In production these come from GitHub Actions repository variables (`.github/workflows/deploy.yml`), not committed files. The two forms deliberately use different `Content-Type`s (`text/plain` for the newsletter form, `application/json` for contact) — see the `wire-form-backend` skill before changing either fetch call, there's a CORS-preflight reason behind the mismatch.

**No Privacy Policy, Terms of Service, or published contact email exist on this site — this is deliberate**, not an oversight (old MSP-era pages, since removed). Don't reintroduce `mailto:`, `/privacy/`, or `/terms/` unless that is explicitly the task.

## Deploy

`main` pushes trigger `.github/workflows/deploy.yml`: `npm run build` (static export to `out/`, using the two `NEXT_PUBLIC_*` repo variables above) then `npx firebase-tools deploy --only hosting` via Workload Identity Federation — no long-lived service account key. `firebase.json` serves `out/` directly. There's no preview-deploy step; verify locally before pushing to `main`.
