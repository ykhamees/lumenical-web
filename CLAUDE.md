@AGENTS.md

## What this is

The marketing site for Lumenical (lumenical.com) — a Next.js 16 App Router site, statically exported and deployed to Firebase Hosting. Dual-audience: SMB consulting (`/services/`) and enterprise platforms (`/platforms/`). This repo also holds two other independently deployed apps: a Python API (`api/`, FastAPI on Cloud Run) backing the two public forms — see "Forms and the API" below — and the admin console (`admin/`, a server-rendered Next.js app on Cloud Run) — see "The admin console" below. `docs/build-plan.md` sequences everything; read it before starting any non-trivial task, and follow its phase order (§12) unless told otherwise. **Neither the API nor the admin console is deployed to live GCP infrastructure yet** — see `docs/infrastructure.md` and `docs/infrastructure-admin.md`.

## Commands

```bash
npm run dev              # dev server, localhost:3000
npm run build            # static export to out/ — this IS the deploy artifact
npm run lint             # eslint .
npx tsc --noEmit         # type-check (no separate script in package.json)
```

There is no test suite and no `test` script — don't invent one unassisted. Before reporting any non-trivial change as done, run `npm run build`, `npm run lint`, and `npx tsc --noEmit`; the `pre-deploy-check` skill (`lumenical-qa` agent) automates this plus route spot-checks and drift checks.

`out/` is regenerated by `npm run build` and `.next/` by `dev`/`build` — both are hook-blocked from direct edits (`.claude/hooks/guard-generated-files.js`). Fix the source instead. A `PostToolUse` hook also auto-lints every `.ts`/`.tsx` file after Write/Edit.

## Architecture

**Routing**: one folder per route under `src/app/` — top-level (`/`, `/services/`, `/platforms/`, `/about/`, `/process/`, `/faq/`, `/careers/`, `/contact/`, `/privacy/`, `/terms/`) plus two dynamic detail routes, `/services/[slug]/` and `/platforms/[slug]/`, generated via `generateStaticParams` from `services.ts`/`platforms.ts`. `next.config.mjs` sets `output: "export"` and `trailingSlash: true` — this must survive any Next.js upgrade, since the site ships as static HTML with no server runtime. `src/content/routes.ts` is the single source of truth for every *top-level* route's path, nav/footer membership, and sitemap inclusion — `navLinks`, `footerLinks`, and (for the static routes) `sitemap.ts` all derive from it; `sitemap.ts` additionally enumerates the dynamic `services`/`platforms` detail pages directly. Adding a top-level route means creating the folder and adding one entry to `routes.ts`; nothing else needs a second edit.

**Content lives in `src/content/`, not inline in JSX**: `site.ts` (name, tagline, description, and the two-audience `audiences` array — each audience carries its own eyebrow/headline/description/stats/differentiators/CTAs, consumed by the homepage and nowhere else), `services.ts` (the `services` array — `slug`, `name`, `summary`, `description`, `features`, plus `engagementLooksLike`/`whatYouGet` for the detail page), `platforms.ts` (the `platforms` array — `slug`, `name`, `summary`, `description`, `features`, `deploymentModes`), and `faq.ts` (the `faqs` array feeding `/faq/` and its `FAQPage` JSON-LD). The homepage, `/services/`, `/services/[slug]/`, `/platforms/`, `/platforms/[slug]/`, and `/faq/` all map over these arrays directly — adding/removing/reordering an entry is the entire change, no separate registration (the detail page, its JSON-LD, breadcrumbs, and sitemap entry all follow automatically). Lumenical is explicitly scoped to exactly six service disciplines and exactly three platform products (AI Platform, Hub, Taskmaster — real products with their own repos); a request for a 7th of either that doesn't clearly fit the existing set needs a check-in rather than being added on assumption. **Platform copy must never name the client behind AI Platform** (a national financial regulator, ~2,000 users, fully on-premises) — no publication sign-off exists (`docs/build-plan.md` O-1); describe it only in that anonymized form.

**Per-page SEO** goes through `pageMetadata()` in `src/lib/seo.ts`, not a bare `export const metadata`. Next.js does not deep-merge a page's `Metadata` with the root layout's — a page that sets only `title`/`description` silently inherits the layout's `openGraph`/`twitter` objects unchanged (wrong title/url in social previews). `pageMetadata({ title, description, path })` fills in the matching `openGraph`/`twitter`/canonical fields; use it in every page. Every route's `opengraph-image.tsx` renders `OgCard` from `src/lib/og.tsx` (the one shared generator + token module all of them import from) rather than duplicating Satori JSX per route.

**Structured data beyond `OrganizationSchema.tsx`** (global, in the root layout): `Breadcrumbs.tsx` renders both the visible breadcrumb nav and its `BreadcrumbList` JSON-LD from one `items` array (every crumb, including the current page, needs an `href`) — used only on the two-level-deep detail routes (`/services/[slug]/`, `/platforms/[slug]/`), not on top-level pages. `ServiceSchema.tsx` and `SoftwareApplicationSchema.tsx` add per-page `Service`/`SoftwareApplication` JSON-LD on those same detail pages. All three follow `OrganizationSchema.tsx`'s existing rule: only facts stated on the page, no invented ratings, prices, or counts.

**Design tokens**: colors (`ink`, `paper`, `signal`, `lumen`, `success`) and font families are defined once in `tailwind.config.ts` and consumed as Tailwind classes — never introduce a raw hex color in a component (`opengraph-image.tsx` is the sole, deliberate exception; Satori can't read Tailwind). `ink-400` is a non-text ink — its only legitimate use is the wordmark's `.ical` (a logo, WCAG-exempt); real text uses `ink-450`/`ink-350` (`text-3` below) instead, which actually clears AA.

**Dark mode** is implemented via `darkMode: "class"` plus a semantic token layer — `bg`, `surface`, `surface-2`, `border`, `border-2`, `text-1`, `text-2`, `text-3`, `text-label`, `text-hover`, `link`, `cta`/`cta-hover`/`on-cta` — each a Tailwind color backed by a CSS custom property with light/dark values in `globals.css` (`:root` and `.dark`). Components use these semantic classes (`bg-surface`, `text-text-2`, …), never the literal `ink-*`/`paper-*`/`bg-white` palette classes, so they render correctly in both themes with no per-component override. `signal-500` is the button/focus-ring accent, not guaranteed-AA text — use `text-link` for text links instead (it fails ~4:1 on `surface-2` in both themes). The `.dark` class is toggled on `<html>` by `ThemeToggle.tsx` and persisted to `localStorage`; a `beforeInteractive` inline script in `layout.tsx` applies the stored (or OS-preferred) theme before hydration to avoid a flash of the wrong theme — `<html>` carries `suppressHydrationWarning` because of this intentional pre-hydration DOM mutation.

Fonts are `next/font/google` (Geist / Instrument Serif / JetBrains Mono) loaded once in `src/app/layout.tsx` and exposed as CSS variables (`--font-sans` etc.); don't add a second font-loading path. Brand voice is restrained, sentence case, no exclamation points, serif italic reserved for one statement per section — the `write-copy` skill / `lumenical-content` agent encode this.

**Forms and the API**: `NewsletterForm.tsx` and `ContactForm.tsx` both `POST` same-origin — `/api/newsletter` and `/api/leads` respectively, both `Content-Type: application/json` — which `firebase.json`'s `hosting.rewrites` sends to the Cloud Run API (`api/`, A-2's whole point: same-origin means no CORS, no preflight, no content-type workaround). Both forms carry a hidden honeypot field (`website`) real visitors never see, and render a Cloudflare Turnstile widget via `Turnstile.tsx` — which renders nothing until `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is set. `NEXT_PUBLIC_SIMULATE_FORMS=true` is a **local-dev-only** escape hatch that makes both forms fake success without calling the API at all — `preview.yml` sets it deliberately (so testing a PR never writes real leads); `deploy.yml` must never set it. The API itself (FastAPI + Pydantic v2 + firebase-admin, `api/app/`) validates, rate-limits (`api/app/rate_limit.py` — a real off-by-one bug here was caught and fixed by testing against the actual Firestore emulator, not just reasoning about the code), verifies Turnstile server-side, writes to Firestore, and best-effort emails via Resend (`api/app/email.py` — a send failure is logged to `outboundEmails` and never fails the request, since the lead is already durably stored). See `api/README.md` for local dev and testing, `docs/infrastructure.md` for what's needed to actually deploy it.

**The admin console (`admin/`)** — leads/newsletter pipeline, pages/demos CMS, media library, audit log, outbound email log — is a separate Next.js app, own `package.json`/`npm run dev|build|lint`, deployed independently to Cloud Run at `web-admin.lumenical.com` (this was `A-4` in `docs/build-plan.md`; superseded 2026-08-22 to segregate the two deployments). Unlike the marketing site it is **not** a static export — `output: "standalone"` — because that's what lets `admin/src/proxy.ts` verify a Firebase session cookie server-side before any admin page renders (real auth gating, not the old client-side-only check). It reaches the Python API only through its own backend-for-frontend proxy (`admin/src/app/api/admin/[...path]/route.ts`), never directly from the browser — that proxy is also the reason `api/`'s Cloud Run service can stay `--no-allow-unauthenticated` without needing CORS. `admin/tailwind.config.ts` and `admin/src/app/globals.css` are a **deliberate duplicate** of the marketing app's design tokens, not shared code — keep both in sync by hand if the design system changes. See `admin/README.md` and `docs/infrastructure-admin.md`.

**Analytics is Plausible** (O-2 — cookieless, no consent banner needed), wired the same env-var-gated way in `layout.tsx`: a no-op unless `NEXT_PUBLIC_PLAUSIBLE_DOMAIN` is set. It's deliberately set only in `deploy.yml`'s repo variables, never `preview.yml`'s, so preview-channel traffic doesn't pollute production numbers. `WebVitalsReporter.tsx` forwards Core Web Vitals to Plausible as a custom event, itself a no-op if Plausible never loaded.

**`/privacy/` and `/terms/` exist and `hello@lumenical.com` is published** (D-4) — this reverses an earlier "deliberately absent" stance from the site's old MSP-era positioning; don't reintroduce that stance. The email never appears as a plain `mailto:` in markup or visible text — `ObfuscatedEmail.tsx` renders inert text in the static HTML and only constructs a real `mailto:` link after a genuine client-side click. Use it (not a raw `mailto:` or plain-text address) anywhere the email needs to appear. It does appear in plain form inside `OrganizationSchema.tsx`'s `contactPoint.email` — that's deliberate (JSON-LD is meant to be machine-read) and not a leak. `/privacy/`/`/terms/` were drafted from a `legal-fact-sheet` run and describe the finalized Phase 3 field list — Turnstile and Resend are named but explicitly noted as **not currently active** (no key configured, API not deployed). Regenerate the fact sheet and update that wording the day the API actually goes live — it's currently forward-looking, not describing live traffic. **Neither page has been reviewed by a lawyer** — `/terms/` in particular omits a governing-law/jurisdiction clause because no fact establishes one; that's a known gap, not an oversight to silently fill in.

## Deploy

`main` pushes trigger `.github/workflows/deploy.yml`: lint, type-check, `npm run build` (static export to `out/`, using the `NEXT_PUBLIC_*` repo variables above) then `npx firebase-tools deploy --only hosting` via Workload Identity Federation — no long-lived service account key. `firebase.json` serves `out/` directly, rewrites `/api/**` to the Cloud Run API, and sets HSTS/CSP-report-only/security headers plus an immutable long-cache for `/_next/static/**`. Pull requests trigger `.github/workflows/preview.yml`, which runs the same lint/type-check/build and deploys to a Firebase preview channel, commenting the preview URL on the PR. A separate `deploy-api.yml`, triggered only on `api/**` changes, lints/type-checks/tests the API (against a real Firestore emulator it starts itself) then builds, pushes, and deploys its container — but its deploy job will fail authentication until `docs/infrastructure.md`'s WIF binding actually exists; the test job needs no GCP access and works today. Likewise, `deploy-admin.yml`, triggered only on `admin/**` changes, lints/type-checks/builds the admin app then builds/pushes/deploys its container to a second Cloud Run service — its deploy job needs `docs/infrastructure-admin.md`'s WIF binding, which doesn't exist yet either.
